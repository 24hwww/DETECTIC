# M4.1-G/H/I — Persistence Investigation

## Objective

Determine whether the stock firmware contains a mechanism that naturally
executes content from writable partitions (`misc_rw`, `runtime_data`, `/var/tmp`,
`/tmp`) at boot time or at any point after boot.

This is the most critical question of M4.1. A writable partition that survives
reboot is necessary but not sufficient for persistence — the firmware must also
*execute* something from it automatically.

## Methodology

1. Exhaustive search of the extracted rootfs (`_rootfs/`) for any script or
   binary that references writable partition paths in an execution context.
2. Analysis of all boot scripts (`rcS`, `rcS.model`, `firmware.sh`).
3. Analysis of all hotplug scripts.
4. Binary string analysis of `cos`, `libcmm.so`, and other daemons.
5. Investigation of the Lifemote `phoenix.sh` remote management feature.
6. Investigation of `INCLUDE_PORTABLE_APP` / `INCLUDE_AGINET_APP_V2`.
7. Check for cron jobs, rcS_hook, overlay systems, and plugin loaders.

## Findings

### 1. Boot scripts — NO writable-path execution

#### `/etc/init.d/rcS` (the main boot script)

- Sources only read-only files: `/etc/config.bba`, `/etc/init.d/rcS.model`.
- Mounts writable partitions (`misc_rw`, `misc_rw_bak`, `runtime_data`) but
  **does not execute anything from them**.
- Copies `/etc/mfg_config.bin` TO `misc_rw/0x00300000` (read-only → writable),
  never the reverse.
- Starts daemons: `cos &`, `cmmsyslogd &` — both are read-only rootfs binaries.
- No `source`/`.`/`exec`/`sh`/`./` commands targeting writable paths.

#### `/etc/init.d/rcS.model`

- Only brings up `eth0`/`eth1`, loads `mii.ko`, creates `/dev` nodes.
- No writable-path execution.

#### `/etc/init.d/firmware.sh` (procd service)

- Only executes read-only hotplug scripts from `/etc/hotplug.d/firmware/`.
- No writable-path execution.

### 2. `/etc/rcS_hook` — EMPTY

```text
$ ls -la _rootfs/etc/rcS_hook/
-rw-r----- 1 ... .gitkeep
```

The directory exists but contains only a `.gitkeep` placeholder. No script in
the firmware sources from this directory.

### 3. Hotplug scripts — NO writable-path execution

All scripts in `/etc/hotplug.d/` were examined:

- `button/00-button`: logs to console only.
- `iface/*`: network event handlers, no writable-path execution.
- `usb/10-usb`: commented out LED updates.
- `firewall/*`: iptables rule management only.
- `dhcp6c/*`: DNS configuration only.

### 4. Cron — NOT STARTED

- BusyBox `crond` is compiled in but **not started** by `rcS`.
- No crontab files exist in the rootfs.
- The default crontab directory is `/etc` (read-only).

### 5. Lifemote `phoenix.sh` — REMOTE download, not local execution

**This is the most interesting finding, but it does NOT provide local
persistence.**

`/usr/bin/phoenix.sh` is a Lifemote remote management script:

```bash
# Downloads a script from a remote URL and executes it from /tmp
cd /tmp
rm /tmp/lifemote_cpe_daemon.sh
while true; do
    if curl --fail -m $MAX_WAIT $LIFEMOTE_AGENT_URL > /tmp/lifemote_cpe_daemon.sh; then
        (sh /tmp/lifemote_cpe_daemon.sh &)&
        break
    fi
    ...
done
```

- It downloads a script from a **remote URL** (`LIFEMOTE_AGENT_URL`) to `/tmp`.
- It executes the downloaded script with `sh`.
- It runs in a supervisor loop, checking every 30 minutes.
- `INCLUDE_LIFEMOTE=y` is set in `config.bba`.
- `libcmm.so` contains `rsl_setDev2LifemoteAgentObj` which starts `phoenix.sh`
  with the format `"/usr/bin/phoenix.sh %s &"` when the
  `Device.X_TP_LIFEMOTE_EXT.LifemoteAgent` data model object is configured.

**Why this is NOT a persistence mechanism for Detectic:**

1. It downloads from a **remote URL**, not from a local writable partition.
2. It requires the Lifemote agent URL to be configured via the data model.
3. It is not started at boot by `rcS` — it is started when the data model
   object is set (by the web UI, a backup restore, or an ISP management system).
4. Even if configured, it downloads from a remote server, not from `misc_rw`.
5. Using it would require either ISP-level access to the Lifemote
   infrastructure or a modified backup to set the URL — both outside M4.1
   constraints.

### 6. WiFi `quick_setting.lua` — system-generated scripts only

`/lib/wifi/quick_setting.lua` executes `sh /tmp/mtk/wifi/<devname>_quick_setting_cmd.sh`
during WiFi reconfiguration. However:

- The script is **generated by the system itself** (not user-provided).
- It is triggered during WiFi configuration changes, not at boot.
- It is not a persistence mechanism.

### 7. `pi_include` — OpenWrt library function, not called at boot

`/lib/functions.sh` contains a `pi_include` function that can source from
`/tmp/overlay/`. However:

- It is a library function, not called by `rcS` or any boot script.
- It is part of the OpenWrt package management system.
- No invocation found in any boot script.

### 8. `INCLUDE_PORTABLE_APP` / `INCLUDE_AGINET_APP_V2` — mobile app integration

These flags enable the TP-Link Aginet mobile app integration (cloud/ISP
management). They do NOT provide a third-party app installation or execution
path. No binary or script loads executables from writable partitions under
these features.

### 9. `cos` daemon — data files only

The `cos` daemon (started at boot by `rcS`) references `/var/tmp/` paths, but
only for data files (`pslist`, `dconf`, `dnsmasq.conf`, etc.). It does not
execute scripts from writable paths.

### 10. `runtime_data` partition — NOT ENABLED

`INCLUDE_RUNTIME_DATA_SECTION` is not set in `config.bba`. The `runtime_data`
UBI partition is not mounted on this firmware build.

## M4.1-H — Safe reboot persistence test

**Not performed.** The investigation above found no legitimate stock mechanism
that could plausibly execute a test artifact from `misc_rw` or any other
writable partition at boot time. Therefore, per the M4.1 instructions, no
reboot test was conducted.

A file merely surviving reboot does NOT prove persistence. Persistence requires
the binary to survive reboot AND the stock firmware to automatically execute it.
No such mechanism exists.

## M4.1-I — Detectic persistence test

**Not performed.** No stock mechanism was found that could automatically start
Detectic after reboot. This test is contingent on M4.1-H, which was not
executed.

## Critical distinction

The investigation distinguishes between:

> "Detectic cannot run on the router"

and:

> "Detectic can run on the router, but cannot automatically start after reboot"

Based on this investigation:

- **Can run**: The binary is architecturally compatible (AArch64, musl, static).
  Runtime execution is expected but unverified due to lack of shell access.
- **Cannot automatically start after reboot**: No stock firmware mechanism
  executes user-provided binaries from writable partitions at boot time.

## Conclusion

The stock firmware does **NOT** contain a mechanism that naturally executes
content from `misc_rw` or any other writable partition at boot time. The only
post-boot execution vector (`phoenix.sh`) downloads from a remote URL, not from
local storage, and requires ISP-level configuration.

Persistence of Detectic on the stock EX520V without firmware modification is
**NOT AVAILABLE** through any legitimate stock mechanism.
