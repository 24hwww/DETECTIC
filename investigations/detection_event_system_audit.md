# DETECTIC Event System — Implementation Audit

This document records the current state of the DETECTIC event pipeline as of the
master mission kickoff. It is the first deliverable of the implementation loop:
`AUDIT → REPRODUCE → ROOT CAUSE → DESIGN → IMPLEMENT → TEST → DEPLOY → VERIFY`.

---

## 1. Architecture at a Glance

```text
EX520
  |
  | GTPR/HTTP IPv6 link-local
  v
host/cli or router-side `detectic` binary
  |
  | site survey / assoc list
  v
Rust sensor (src/service.rs, src/temporal.rs)
  |
  | canonical EventEnvelope batch
  | HTTP POST /api/v1/events
  | HMAC-SHA256, replay ±300s
  v
Cloudflare Worker (backend/cf-worker/src/index.ts)
  |
  | D1 SQL
  v
D1 Database
  |
  | GET /api/v1/*
  v
Dashboard HTML (20s polling)
```

The sensor is **push-only HTTPS**. The frontend is **pull-only polling**. There
is currently **no persistent full-duplex channel** and **no server-initiated
push** to the browser.

## 2. Database Schema (D1)

File: `backend/cf-worker/schema.sql`

Existing temporal/event tables:

| Table | Purpose | Key Temporal Fields |
|---|---|---|
| `events` | raw event envelope log | `event_timestamp`, `received_at`, `event_id`, `sequence` |
| `device_state` | current device summary | `first_seen`, `last_seen`, `updated_at`, `total_connected_time`, `connection_count` |
| `device_sessions` | connection sessions | `started_at`, `ended_at`, `duration_seconds`, `received_at` |
| `ap_state` | current AP/network state | `first_seen`, `last_seen`, `online_since`, `updated_at` |
| `ap_sessions` | AP sessions | `started_at`, `ended_at`, `duration_seconds`, `received_at` |
| `rf_environment_snapshots` | per-survey RF summary | `event_timestamp`, `received_at` |
| `snapshots` | legacy v1 ingestion | `captured_at`, `received_at` |
| `detections` | legacy v1 per-device per-snapshot | (no event time) |

Indexes exist for:
- `events(sensor_id)`, `events(device_id)`
- `device_sessions(sensor_id, device_id)`, `device_sessions(started_at)`
- `ap_state(sensor_id, status)`, `ap_state(sensor_id, last_seen)`
- `rf_environment_snapshots(sensor_id, event_timestamp)`

**Audit conclusion:** The schema already supports chronological event history,
connection sessions, durations, and signal state. What is missing are the
**read paths** (APIs and UI) and the **real-time fan-out** layer.

## 4. Sensor → Cloudflare Transport

### What works
- HMAC-signed HTTPS POST with `X-Detectic-Sensor`, `X-Detectic-Signature`,
  `X-Detectic-Timestamp`.
- The binary can be built with `--features tls` using `rustls` + `webpki-roots`;
  this was proven on a real EX520 during P5 validation.
- A bounded in-memory `ReliableQueue` and on-disk `SpoolEventTransport` exist
  for buffering (exponential backoff 1/2/4s, max 3 attempts, 64 KB spool).

### What is broken
- **ACK contract mismatch**:
  - Worker returns `202 { accepted, duplicates }` (`backend/cf-worker/src/index.ts:486`)
  - Sensor expects `200 { accepted_ids: [...] }` (`src/event_transport.rs:134-141`)
  - Result: the sensor parses an empty `accepted_ids` array, treats the batch as
    un-acknowledged, and **keeps it in the spool** even though the Worker
    already persisted it. Log evidence: `events_flush sent=0 kept=62`.
- **HTTP 202 semantics:** because 202 < 300, the sensor does not treat it as a
  permanent HTTP error; it reaches the JSON parser. The mismatch is in the
  payload shape, not the status code.

### WebSocket / WSS capability
- **No WebSocket crate is linked.** `Cargo.toml` has `ureq` only.
- AGENTS.md explicitly marks `WebSocket: NO-GO for EX520 stock` because
  persistent TCP libraries would add size, C dependencies, or async complexity.
- No explicit capability test has been run in this session. The most feasible
  real-time transport remains **HTTPS POST from sensor + push channel from
  backend to frontend**, not a WSS client inside the router.

## 6. Frontend Audit

File: `backend/cf-worker/src/dashboard.html`

- **Transport:** 20-second HTTP polling via `setInterval(poll, 20000)`. No
  WebSocket, no SSE, no EventSource.
- **Displayed data:**
  - device list with class, vendor, RSSI, band, first/last seen (relative)
  - AP/network list
  - aggregate stats
  - 24h RSSI scatter, activity bar, class doughnut charts
- **What is missing:**
  - live event stream
  - historical timeline filter
  - per-device event / signal / connection history
  - explicit timezone display (uses `toLocaleTimeString`, so it is browser-local
    but not labeled)
  - pagination
  - real-time reconnect/loading/error states

## 7. Email Reporting Audit

Files: `src/notifier/mod.rs`, `src/notifier/template.rs`, `src/notifier/smtp.rs`

- **Rust SMTP notifier is implemented:** supports Brevo/SMTP, TLS, queue, rate
  limiting, retry backoff.
- **Email is event-driven only:** triggered on `DeviceJoined`, `DeviceLeft`,
  `DeviceUpdated` (the latter disabled by default).
- **Template is a single-event snapshot:** includes `captured_at` timestamp,
  total/connected counts, hostname, masked MAC, IP, RSSI, band, channel, but
  **no report period, no connection start/end, no session duration, no
  historical signal timeline**.
- **Python `emaild.py` is referenced in launcher/docs but missing from the
  repo.** It would have provided periodic `type=startup` and `type=report` GET
  hooks.

## 8. Root Causes Identified

1. **Sensor thinks uploads failed** because the Worker ACK payload does not
   match the sensor's `accepted_ids` expectation.
2. **No real-time fan-out** exists. The sensor pushes, but the Worker does not
   push to the frontend; the dashboard polls every 20 seconds.
3. **Historical data exists in D1 but is not exposed** through the required
   `GET /api/events`, `GET /api/devices/:id/events`, etc.
4. **Email is per-event, not report-based**, and lacks durations/history.
5. **Timezone and explicit timestamp formatting** are not implemented in the
   frontend.
6. **WebSocket/WSS from the EX520 has not been proven**, and the project
   documentation currently marks it as not viable on stock firmware.

---

## 9. Recommended First Slices (Minimal Fixes)

### Slice 1 — Fix the ACK contract
- Worker: return `200` with `accepted_ids` array.
- OR sensor: parse `accepted` count and treat `accepted > 0` as success.
- This immediately makes the existing pipeline correct and stops spurious
  spool growth.

### Slice 2 — Historical event APIs
- Add `GET /api/v1/events` (sensor, device, type, time range, pagination).
- Add `GET /api/v1/devices/:pseudonym/events`.
- Add `GET /api/v1/devices/:pseudonym/signals`.
- Add `GET /api/v1/sensors/:id/events`.

### Slice 3 — Frontend history view
- Add a `/history` view or dashboard tab with filters and paginated API calls.
- Show local time with timezone label.

### Slice 4 — Real-time fan-out (backend→frontend)
- Use Cloudflare Durable Objects + WebSocket or SSE for `GET /api/v1/live`.
- Worker pushes newly-ingested events to connected clients.
- This satisfies "real-time" without requiring the router to maintain a WSS
  client.

### Slice 5 — Periodic email report
- Extend `DetectionEvent` / create a report generator that queries D1 for a
  period and builds a report with period, counts, connection history, signal
  stats, durations.
- Trigger from a scheduled Worker cron or from the missing `emaild` endpoint.

### Slice 6 — WebSocket capability test
- Build a minimal `wss` probe for the EX520 only to explicitly measure latency
  and stability before designing around WSS.
